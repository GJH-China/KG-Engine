# 架构说明 · Architecture

## 模块结构

```
kaederonm_kg/
├── __init__.py     入口，导出公开 API
├── features.py     特征提取（1,272 行）—— 项目的核心工作量在这里
├── model.py        加权朴素贝叶斯学习器与预测器
├── store.py        模型持久化（原子写 / 世代滚动 / 校验和）
├── baseline.py     良性基线采集（冷启动用）
├── feed.py         投喂调度（按扩展名分拣、去重、限流）
└── _pathsafe.py    路径安全判断（防 .. 穿越与软链逃逸）
```

依赖关系是单向的：`__init__` → 其余模块，其余模块之间只有 `baseline` → `feed` / `_pathsafe`。
没有循环依赖，任何一个模块都可以单独摘出去用。

## 数据流

```
文件字节
   │
   ├─ 扩展名判定 ──→ binary 通道 或 text 通道
   │
   ├─ 归档探测 ──→ 若为 zip/7z/tar，安全递归展开（有层数、字节、成员数三重上限）
   │
   ├─ 特征提取 ──→ FeatureVector { counts: {特征名: 次数}, labels: {元信息} }
   │
   ├─ learn()   ──→ 累加对应通道的 (特征, 类别) 计数
   │
   └─ predict() ──→ 逐特征算加权对数似然比 → 求和 → score
                                  │
                                  └─→ contributions: [(特征, 贡献), ...]
```

## 特征体系

`features.py` 是整个项目最重的部分（1,272 行），因为"用什么特征"直接决定模型上限。
特征名带前缀，可读且能直接用于解释：

| 前缀 | 含义 | 例子 |
|---|---|---|
| `b` | 字节 n-gram 哈希桶 | `b448`、`b8bc3` |
| `f_entropy_` | 香农熵分档 | `f_entropy_7` |
| `f_size_log` | 文件大小 log2 分档 | `f_size_log_18` |
| `pe_` | PE 结构特征 | `pe_section_rwx`、`pe_no_imports` |
| `str_` | 字符串模式 | `str_powershell_enc` |

**字节 n-gram 用哈希桶而不是完整 n-gram**，原因是完整的二元组在自然二进制里有 65536 种，
三元组更是天文数字，直接存会让模型文件膨胀到几百 MB。哈希到固定桶数后，
模型体积可控（KG2c 只有 380 KB），代价是少量哈希碰撞。

## 为什么用朴素贝叶斯

考虑过也否决过的方案：

| 方案 | 否决理由 |
|---|---|
| 随机森林 / GBDT | 需要 numpy + sklearn，安装包体积和依赖链都不可控 |
| 神经网络 | 同上，且小语料下容易过拟合，还失去可解释性 |
| 完整 n-gram 表 | 模型文件会到几百 MB，加载慢、分发难 |
| **加权朴素贝叶斯** | ✅ 纯标准库、增量更新、逐特征可解释、模型只有几百 KB |

朴素贝叶斯的前提假设（特征独立）在二进制数据上**明显不成立**——PE 节区的可写属性
和熵必然相关。但实测 AUC 仍在 0.98 以上，说明这个假设的破坏程度尚可接受。
这是有意识的取舍，不是没想到。

## 模型存储格式

`model.json` **不是纯 JSON**，而是三层结构：

```
raw[:8]        8 字节 ASCII 头长度 H
raw[8:8+H]     head JSON  { format, sha256, len }
raw[8+H:]      body JSON  { format, kind, saved_at, stats, model }
```

为什么这么设计：

1. **先读长度再解析**，可以在不反序列化整个 body 的情况下判断文件是否完整
2. **body 带 SHA-256**，坏档能立刻发现，不会把半个模型读进内存
3. **原子写**：先写临时文件再 `os.replace`，断电不会留下半截文件
4. **世代滚动**：每次保存保留上一代（`model.001.json`），出问题能 `rollback()`
5. **单调性守卫**：新模型的样本数少于磁盘上的旧模型时**拒写**（除非 `force=True`）——
   防止"旧内存态静默覆盖新档"这种极难排查的事故

## 安全考量

处理恶意样本本身就是危险操作，所以 `features.py` 里有这些约束：

- **归档递归有硬上限**：层数、累计解压字节数（32 MB）、成员数（4,096）、
  单成员字节数，任一超限即停。防 zip bomb。
- **路径穿越防护**：归档内成员若解出 `../..` 路径，一律拒绝（`_pathsafe.is_within`）。
- **不执行、不解析脚本**：只会读字节，绝不 `exec` / `eval` 任何被检测内容。

## 已知架构局限

- 特征是**静态**的，看不到运行行为。
- 加壳/加密样本的字节分布接近随机，统计特征几乎失效。
- 字节 n-gram 对**编译器/打包器**敏感：同一个作者用同一套工具链打出来的良性软件
  和恶意软件，字节分布会很像。这是安装包类文件容易被误报的根本原因。
